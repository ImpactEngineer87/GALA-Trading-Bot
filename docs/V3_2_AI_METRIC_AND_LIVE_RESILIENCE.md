# v3.2 AI Metric and Live Resilience Design

## Why the August and September percentages can differ

The values shown in the AI retraining table are evaluation metrics generated by
retraining runs, not permanent properties of a ticker and not the live AI
probability of the current signal.

Each retraining run uses a later chronological dataset and creates new FIT,
VALIDATION, and untouched TEST windows. Therefore a Candidate Balanced Accuracy
from August should not be expected to equal a Candidate Balanced Accuracy from
September.

v3.2 adds an evaluation ID/time/window so the dashboard makes that distinction
explicit.

## The stale-incumbent display defect fixed in v3.2

The previous lifecycle state updated the incumbent BA only when the current run
returned one. If the next evaluation had no incumbent comparison, the old
incumbent value could remain in state while the candidate BA was refreshed.
That made a cross-run comparison appear valid when it was not.

v3.2 replaces the entire evaluation snapshot atomically, including `null`
incumbent values. Candidate/SHADOW incumbent/PRODUCTION incumbent are therefore
never intentionally mixed across retraining runs.

## Why UAL can say SHADOW ACCEPTED but REAL is blocked

Those are two different gates:

- **SHADOW acceptance** decides whether the new candidate is useful enough to be
  retained in the non-production candidate tier.
- **PRODUCTION gate** applies the stricter rules required for normal REAL model
  promotion.

A candidate may improve the SHADOW incumbent yet fail production because of one
of the other configured requirements, for example winner recall, precision
lift, approval rate, loser filtering, or degradation compared with the current
PRODUCTION model.

v3.2 shows the exact production failure reason instead of a generic boolean.
The audited manual override remains available but does not rewrite the failed
production gate to PASS.

## Decision threshold vs Balanced Accuracy

These numbers have different meanings:

- **Decision threshold** (for example 43% or 62%): the probability cutoff used
  by that specific model to approve/veto a signal.
- **Balanced Accuracy** (for example 60.88%): an evaluation metric on a labeled
  chronological TEST dataset.
- **Live signal probability**: the model output for one current signal.

They are not expected to match numerically. v3.2 changes dashboard labels to
make this distinction explicit.

## Useful vs missed AI vetoes

For resolved veto observations:

- `veto_usefulness_pct` = percentage of comparable vetoes that would have
  avoided a losing trade.
- `veto_missed_winner_pct` = percentage of comparable vetoes that would have
  blocked a winning trade.

This gives the client a direct answer to whether the filter is helping in REAL
or PAPER observations instead of relying on a raw number of vetoes.

## Mixed PAPER + REAL startup

v3.0.7/v3.1.1 could reject the whole startup when one REAL ticker failed broker
preflight. v3.2 introduces a partitioned validator.

Example:

```text
META REAL  -> no valid 1m candles after retries -> META -> PAPER
NVDA REAL  -> broker preflight PASS             -> remains REAL
UAL PAPER  -> unaffected                         -> remains PAPER
```

Global controls are not partitioned. Missing explicit live arm, unsafe scheduler
mode, disabled daily-loss protection, or unavailable global validators still
stop the engine.
